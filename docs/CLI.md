# gusto command reference

This file is generated by `gusto help --markdown`. Edit the command table in the source, not this file.

gusto runs the AI agents you already use, each in a sandbox, on a task.

## Commands

**Run a task**

- [`gusto new`](#gusto-new): Make a task directory: repository, brief and check
- [`gusto run`](#gusto-run): Do a task in a container
- [`gusto inside`](#gusto-inside): Do a task here, without a container
- [`gusto submit`](#gusto-submit): Send a task to a server and watch it there
- [`gusto show`](#gusto-show): What a task asked for and what happened
- [`gusto rerun`](#gusto-rerun): Run finished tasks again and compare the verdicts
- [`gusto compare`](#gusto-compare): Run one task on two agents, side by side
- [`gusto benchmark`](#gusto-benchmark): Run tasks on agent and model pairs, as a table

**Send and prove**

- [`gusto pr`](#gusto-pr): Open a pull request from a task, or verify one
- [`gusto verify`](#gusto-verify): Check a task's record: hashes, signer and check
- [`gusto export`](#gusto-export): Write an audit record anyone can verify

**Run gusto**

- [`gusto serve`](#gusto-serve): Serve the pages: submit a task, watch it, read the record
- [`gusto open`](#gusto-open): Open gusto on this computer in the browser, signed in
- [`gusto local`](#gusto-local): Run gusto for one person on this computer
- [`gusto cloud`](#gusto-cloud): Run gusto cloud, the hosted server for accounts and routing
- [`gusto host`](#gusto-host): Run a host for organisations' servers, for a gusto cloud
- [`gusto operator`](#gusto-operator): Serve the operator's page for a gusto cloud, on loopback
- [`gusto scan`](#gusto-scan): Ask the runner image which agents it carries
- [`gusto doctor`](#gusto-doctor): Check this computer can run a task, before one is sent

**Account**

- [`gusto login`](#gusto-login): Sign this computer in as you, by your organisation's server
- [`gusto logout`](#gusto-logout): End this computer's sign-in and forget it
- [`gusto whoami`](#gusto-whoami): Who this computer is signed in as

**Records, keys and data**

- [`gusto keygen`](#gusto-keygen): Make a key pair to sign records with
- [`gusto keys`](#gusto-keys): Which key signed each record
- [`gusto changes`](#gusto-changes): Check a record of platform changes
- [`gusto retention`](#gusto-retention): List what a retention sweep would remove now
- [`gusto data`](#gusto-data): Show, check and roll back the format of the data
- [`gusto spend`](#gusto-spend): What the tasks spent this month, by team, project and task
- [`gusto usage`](#gusto-usage): Search the model calls the agents made, by session

**Other**

- [`gusto agents`](#gusto-agents): List the agents this binary knows
- [`gusto version`](#gusto-version): Print the release
- [`gusto help`](#gusto-help): Show help for gusto or one command

## Exit codes

- `0`: success
- `1`: failure, including a check that failed
- `2`: usage error

## `gusto new`

Make a task directory: repository, brief and check

```text
gusto new <dir> -repo <url> -brief <text> [-agent <name>] -- <check command>
```

Makes the directory a task lives in and writes what it asks for: the repository to work in, what to do, the agent and the check. The check is the command whose exit code says pass or fail. Everything after -- is the check.

Arguments:

- `<dir>`: where to make the task

Flags:

- `-agent <string>`: which agent does the work, from gusto agents (default opencode)
- `-brief <words>`: what to do, in your words
- `-model <model>`: the model to ask for
- `-repo <url>`: the url of the repository to work in
- `-sensitivity <label>`: label the task: public, internal or restricted (default internal)
- `-h, --help`: show this help

Examples:

```sh
gusto new fix-login -repo https://github.com/acme/app \
    -brief "Fix the redirect after login" -- npm test
```

See also: `gusto run`, `gusto inside`, `gusto agents`

## `gusto run`

Do a task in a container

```text
gusto run <dir>
```

Checks the repository out here, so that a repository credential stays on this computer and never enters the container with the agent, then runs the agent and the check in a container. The exit code is the check's answer.

Arguments:

- `<dir>`: the task directory made by gusto new

Flags:

- `-h, --help`: show this help

Environment:

- `GUSTO_CONTAINER`: the container runtime to use, docker or podman
- `GUSTO_IMAGE`: the runner image tasks run in
- `GUSTO_MODEL_URL`: the model endpoint the agent calls
- `GUSTO_MODEL_TOKEN`: the key for that endpoint
- `GUSTO_SIGNING_KEY`: the private key the record is signed with, from gusto keygen

Exit codes:

- `0`: the check passed
- `1`: the check failed, or the task could not be run
- `2`: usage error

Examples:

```sh
gusto run fix-login
```

See also: `gusto inside`, `gusto verify`, `gusto show`

## `gusto inside`


Arguments:

Flags:

- `-h, --help`: show this help

Environment:

- `GUSTO_MODEL_URL`: the model endpoint the agent calls
- `GUSTO_MODEL_TOKEN`: the key for that endpoint
- `GUSTO_SIGNING_KEY`: the private key the record is signed with, from gusto keygen

Exit codes:

- `0`: the check passed
- `1`: the check failed, or the task could not be run
- `2`: usage error

Examples:

```sh

```

See also: `gusto run`, `gusto verify`

## `gusto submit`

Send a task to a server and watch it there

```text
gusto submit <dir>
```

Sends the task to a gusto server instead of running it here, so the work outlives your shell. Prints the task's id and its address on the server.

Arguments:

- `<dir>`: the task directory made by gusto new

Flags:

- `-h, --help`: show this help

Environment:

- `GUSTO_SERVER`: the server, with its scheme, such as https://gusto.example.com
- `GUSTO_TOKEN`: an API token from the server's Tokens page
- `GUSTO_PASSWORD`: the server's shared sign-in, when it has no tokens

Examples:

```sh
GUSTO_SERVER=https://gusto.example.com gusto submit fix-login
```

See also: `gusto serve`, `gusto show`

## `gusto rerun`

Run finished tasks again and compare the verdicts

```text
gusto rerun <dir>... [-into <dir>] [-here]
```

Runs each finished task again at the commit it started from, and prints one summary of how the verdicts changed. Give a task directory, or a directory of tasks.

Arguments:

- `<dir>...`: task directories, or a directory of them

Flags:

- `-here`: run here, without a container
- `-into <directory>`: where the reruns go, as a directory; beside each task by default
- `-h, --help`: show this help

Environment:

- `GUSTO_CONTAINER`: the container runtime to use, docker or podman
- `GUSTO_IMAGE`: the runner image tasks run in

Exit codes:

- `0`: every verdict held or improved
- `1`: a verdict got worse
- `2`: a task could not be rerun, or a usage error

Examples:

```sh
gusto rerun tasks/
gusto rerun fix-login -here
```

See also: `gusto compare`, `gusto benchmark`

## `gusto compare`

Run one task on two agents, side by side

```text
gusto compare <dir> <agent> <agent> [-into <dir>] [-here]
gusto compare <comparison>
```

Runs one task on each agent as one comparison, or prints a comparison that already ran. It exits 0 when every side ran and its record checks, whichever agent did better.

Arguments:

- `<dir>`: the task directory
- `<agent>`: an agent from gusto agents
- `<comparison>`: a comparison directory that already ran

Flags:

- `-here`: run here, without a container
- `-into <directory>`: where the comparison goes, as a directory; beside the task by default
- `-h, --help`: show this help

Environment:

- `GUSTO_CONTAINER`: the container runtime to use, docker or podman
- `GUSTO_IMAGE`: the runner image tasks run in

Exit codes:

- `0`: every side ran and its record checks
- `2`: a side did not, or a usage error

Examples:

```sh
gusto compare fix-login claude-code codex
```

See also: `gusto agents`, `gusto benchmark`

## `gusto benchmark`

Run tasks on agent and model pairs, as a table

```text
gusto benchmark <plan> [-into <dir>] [-here] [-again <pairs>] [-json]
```

Runs a plan's tasks on every agent and model pair it names, and prints a table of which finish, or prints a benchmark that already ran. In a container each run goes out as a server's task does, through the proxy when a credential is held, so its cost is the proxy's count. It exits 0 when every run left a verdict and its record checks.

Arguments:

- `<plan>`: a plan file, or a benchmark directory that ran

Flags:

- `-again <all>`: run finished pairs again: all, or agent@model,...
- `-here`: run here, without a container
- `-into <directory>`: where the benchmark goes, as a directory; beside the plan by default
- `-json`: print the table as the catalog reads it
- `-h, --help`: show this help

Environment:

- `GUSTO_SANDBOX`: openshell runs each task in an OpenShell sandbox
- `GUSTO_CONTAINER`: the container runtime to use, docker or podman
- `GUSTO_IMAGE`: the runner image tasks run in

Exit codes:

- `0`: every run left a verdict and its record checks
- `2`: a run did not, or a usage error

Examples:

```sh
gusto benchmark plan.json
gusto benchmark plan.json -again all
```

See also: `gusto compare`, `gusto rerun`

## `gusto pr`

Open a pull request from a task, or verify one

```text
gusto pr <command> [arguments]
```

A task whose check passed can become a pull request carrying its record, and anybody can check that record from the repository alone.

Commands:

- `open`: Push a passed task's patch and open a pull request
- `verify`: Fetch a pull request's record and verify it

Flags:

- `-h, --help`: show this help

See also: `gusto verify`, `gusto export`

### `gusto pr open`

Push a passed task's patch and open a pull request

```text
gusto pr open <dir> [-dry-run] [-remote <url>] [-github <owner/name>] [-base <branch>]
```

Pushes the patch of a task whose check passed and opens a pull request that carries the task's record and the command that verifies it. A dry run prints what would happen and does none of it, and needs no token.

Arguments:

- `<dir>`: the task directory

Flags:

- `-base <branch>`: the branch the pull request targets
- `-dry-run`: print what would happen, and do none of it
- `-github <owner/name>`: owner/name on GitHub, read off the remote by default
- `-remote <url>`: where to push, as a url; the task's repository by default
- `-h, --help`: show this help

Environment:

- `GUSTO_GITHUB_TOKEN`: the standing token to push and open with, when there is no GitHub App
- `GUSTO_KEYRING`: the directory of public keys that name a record's signer

Exit codes:

- `0`: the pull request was opened, or printed by a dry run
- `1`: the task must not be sent, or something went wrong
- `2`: usage error

Examples:

```sh
gusto pr open fix-login -dry-run
gusto pr open fix-login
```

See also: `gusto pr verify`, `gusto verify`

### `gusto pr verify`

Fetch a pull request's record and verify it

```text
gusto pr verify <repo> <sha256> [-into <dir>]
```

Verifies a pull request's record from the repository alone. This is the command gusto pr open prints in every pull request it opens.

Arguments:

- `<repo>`: the repository the pull request is in
- `<sha256>`: the hash of the record's manifest, as the pull request gives it

Flags:

- `-into <directory>`: unpack the task in this directory and keep it, rather than in one removed afterwards
- `-h, --help`: show this help

Exit codes:

- `0`: everything agrees
- `1`: something does not, and the output names it, or the check could not be made
- `2`: usage error

Examples:

```sh
gusto pr verify https://github.com/acme/app 3f2a9c...
```

See also: `gusto pr open`, `gusto verify`

## `gusto verify`

Check a task's record: hashes, signer and check

```text
gusto verify <dir> [-signed]
```

Hashes the task's files again and compares them with the record, names the signer from the keyring, and runs the check again. The exit code is 0 when everything agrees and 1 when anything does not.

Arguments:

- `<dir>`: the task directory

Flags:

- `-signed`: refuse a record that no key signed
- `-h, --help`: show this help

Environment:

- `GUSTO_KEYRING`: the directory of public keys that name a record's signer

Exit codes:

- `0`: the files match, and the check still gives its recorded answer
- `1`: a file changed, the signature fails, or the check now answers differently
- `2`: usage error

Examples:

```sh
gusto verify fix-login -signed
```

See also: `gusto pr verify`, `gusto export`, `gusto keys`

## `gusto export`

Write an audit record anyone can verify

```text
gusto export <dir> [-to <dir>] [-policy <file>] [-requests <file>]
gusto export -verify <export dir>
```

Writes a task's record as an audit export in a new directory, dropping and redacting what the policy says. With -verify it checks an export instead of writing one.

Arguments:

- `<dir>`: the task directory, or with -verify the export directory

Flags:

- `-policy <file>`: a JSON file saying what the export drops and redacts
- `-requests <string>`: the server's request log, one JSON line a request
- `-to <directory>`: the new directory to write the export into (default <dir>.audit)
- `-verify`: check an export instead of writing one
- `-h, --help`: show this help

Environment:

- `GUSTO_KEYRING`: the directory of public keys that name a record's signer

Examples:

```sh
gusto export fix-login
gusto export -verify fix-login.audit
```

See also: `gusto verify`

## `gusto serve`

Serve the pages: submit a task, watch it, read the record

```text
gusto serve
```

Runs the gusto server: the pages for submitting a task, watching it and reading its record, and the queue that runs tasks. It will not start without GUSTO_PASSWORD. Many more settings, for sign-in, limits, models and storage, are read from GUSTO_ variables; docs/REFERENCE.md lists them.

Flags:

- `-h, --help`: show this help

Environment:

- `GUSTO_PASSWORD`: the server's shared sign-in; required
- `GUSTO_ADDR`: where to listen (default 127.0.0.1:8040)
- `GUSTO_JOBS`: the directory tasks are kept in (default jobs)
- `GUSTO_SESSIONS`: the directory agents' conversations are kept in (default sessions)
- `GUSTO_SANDBOX`: how tasks are held: container, openshell, process or here
- `GUSTO_JOB_CONCURRENCY`: how many tasks run at once (default 1)
- `GUSTO_MODELS`: the models the server offers
- `GUSTO_OIDC_ISSUER`: sign people in through this OpenID Connect issuer
- `GUSTO_ALLOWED`: the people who may sign in, separated by commas
- `GUSTO_ADMINS`: the people who administer the server
- `GUSTO_API_TOKENS`: the file of API tokens
- `GUSTO_RETENTION`: the directory of the retention policy and holds
- `GUSTO_REGISTRY`: the directory of the organisation's registry of models

Examples:

```sh
GUSTO_PASSWORD=secret gusto serve
```

See also: `gusto local`, `gusto cloud`, `gusto doctor`

## `gusto local`

Run gusto for one person on this computer

```text
gusto local <command> [arguments]
```

Gusto for one person on their own computer: it starts when you sign in, listens on the loopback only, and keeps its data in your account's data folder.

Commands:

- `install`: Start gusto at login and open it
- `run`: Run gusto in this terminal; what the service runs
- `stop`: Stop the gusto service
- `uninstall`: Stop starting gusto at login
- `link`: Print a new sign-in link and open nothing
- `use`: Add a model key from your shell to gusto
- `sandbox`: Install or remove the virtual machine sandbox

Flags:

- `-h, --help`: show this help

Environment:

- `GUSTO_LOCAL_HOME`: where gusto keeps your work, instead of the system's place for an app's data
- `GUSTO_KEYCHAIN`: off keeps model keys in files only you can read, not in the keychain

See also: `gusto open`, `gusto doctor`

### `gusto local use`

Add a model key from your shell to gusto

```text
gusto local use <NAME> [<model>...]
```

Adds the key in one of your environment variables to your own gusto, with the models you name, or the one you pick from what the provider lists. The key goes to this computer's keychain and nowhere else.

Arguments:

## `gusto cloud`

Run gusto cloud, the hosted server for accounts and routing

```text
gusto cloud
gusto cloud workspaces
```

With no subcommand, runs gusto cloud: sign-up, sign-in and the organisations' records, and the servers it starts for each organisation and sends their people to. It runs no tasks itself. Its settings are the GUSTO_CLOUD_ variables; docs/CLOUD.md lists them.

Commands:

- `workspaces`: List every workspace on this host

Flags:

- `-h, --help`: show this help

Environment:

- `GUSTO_CLOUD_ADDR`: where to listen (default 127.0.0.1:8050)
- `GUSTO_CLOUD_URL`: the address links in mail begin with, such as https://cloud.example.com
- `GUSTO_CLOUD_ROOT`: the directory gusto cloud keeps its records in (default cloud)
- `GUSTO_CLOUD_DOMAIN`: the domain organisations' servers are under
- `GUSTO_CLOUD_ORG_ENV`: a file of KEY=VALUE lines every organisation's server starts with

Examples:

```sh
gusto cloud
gusto cloud workspaces
```

See also: `gusto host`, `gusto operator`

### `gusto cloud workspaces`

List every workspace on this host

Flags:

## `gusto host`

Run a host for organisations' servers, for a gusto cloud

```text
gusto host
```

Runs the agent on a host that runs organisations' servers for a gusto cloud on another. It starts and stops what gusto cloud asks, signed with the secret they share, and says every few seconds that it is there.

Flags:

- `-h, --help`: show this help

Environment:

- `GUSTO_CELL_NAME`: what this host is called: lower case letters, digits and hyphens, up to 31
- `GUSTO_CELL_PRIVATE`: this host's IPv4 address on the private network, which its servers bind to
- `GUSTO_CELL_PORT`: the port to listen on (default 8060)
- `GUSTO_CELL_SECRET_FILE`: the file with the secret gusto cloud and the hosts sign with
- `GUSTO_CELLS_DIR`: the directory every host and gusto cloud see

See also: `gusto cloud`

## `gusto operator`

Serve the operator's page for a gusto cloud, on loopback

```text
gusto operator
```

Serves the page an operator manages a gusto cloud from. It listens on the loopback of the machine gusto cloud runs on and refuses any other address, so nothing gusto cloud serves can reach it. Open a tunnel to it.

Flags:

- `-h, --help`: show this help

Environment:

- `GUSTO_OWNER_ADDR`: where to listen; a loopback address (default 127.0.0.1:8090)
- `GUSTO_CLOUD_ROOT`: the directory gusto cloud keeps its records in (default cloud)

See also: `gusto cloud`

Make a key pair to sign records with

```text
gusto keygen <name> [-dir <dir>] [-awskms <key>]
```

Writes a signer's key pair: the private key for GUSTO_SIGNING_KEY on the machine that runs tasks, and the public key for every verifier's GUSTO_KEYRING, where its file name is the name verify gives the signer. With -awskms the private key stays in AWS KMS and only the public key is written.

Arguments:

- `<name>`: what the signer is called

Flags:

- `-awskms <key>`: an AWS KMS key to sign with instead: its id, ARN or alias
- `-dir <string>`: where to write the two files (default .)
- `-h, --help`: show this help

Environment:

- `GUSTO_SIGNING_KEY`: the private key the record is signed with, from gusto keygen
- `GUSTO_KEYRING`: the directory of public keys that name a record's signer

Examples:

```sh
gusto keygen ci -dir keys
```

See also: `gusto keys`, `gusto verify`

## `gusto usage`

Search the model calls the agents made, by session

```text
gusto usage <command> [arguments]
```

The index of model calls is built from each task's proxy record (out/proxy.jsonl), which stays the record. These commands read the index and rebuild it. A rebuilt index holds the same rows as the one it replaces.

Commands:

- `sessions`: List sessions with what they spent, the most recently used first
- `reindex`: Fill the index from the tasks' records now

Flags:

- `-h, --help`: show this help

### `gusto usage sessions`

List sessions with what they spent, the most recently used first

```text
gusto usage sessions [-person <who>] [-agent <name>] [-agent-type <type>] [-provider <name>] [-model <name>] [-month <2006-01>] [-limit <n>] [-tasks <dir>] [-json]
```

Lists the sessions that have a call matching the flags. A session is the calls of one conversation, or of one task that is in none. The cost counts only calls the models' prices were known for: a cost ending in + leaves out some calls, and n/a is a session none of whose calls have a price. Cache is the share of input tokens the provider's cache answered.

Flags:

- `-agent <agent>`: only this agent, by the name its person gave it
- `-agent-type <agent type>`: only this agent type, the program that made the calls
- `-json`: print the sessions as JSON
- `-limit <sessions>`: the most sessions to list (default 20)
- `-model <model>`: only calls to this model
- `-month <2006-01>`: only calls in this month, as 2006-01
- `-person <person>`: only this person's sessions
- `-provider <provider>`: only calls this provider answered
- `-tasks <directory>`: the directory the server keeps tasks in (default $GUSTO_JOBS, else jobs)
- `-h, --help`: show this help

Environment:

- `GUSTO_DATABASE_URL`: where the index is kept: empty for usage.db beside the tasks directory, or a postgres:// address (a search_path parameter names the schema)
- `GUSTO_JOBS`: the directory of tasks, when -tasks is not given (default jobs)

Exit codes:

- `0`: success, including when no session matches
- `1`: the index could not be read
- `2`: usage error

Examples:

```sh
gusto usage sessions -month 2026-10
gusto usage sessions -person ada@acme.com -provider anthropic -json
```

See also: `gusto usage reindex`, `gusto spend`

### `gusto usage reindex`

Fill the index from the tasks' records now

```text
gusto usage reindex [-from-scratch] [-tasks <dir>]
```

Reads the model calls the index does not hold from every task's proxy record and adds them, printing how far it has got. It can be run again at any time and picks up where an interrupted run stopped. With -from-scratch it first removes every row, says how many, and rebuilds them all. A task that retention removed has no record to read, so a rebuild from scratch leaves its calls out.

Flags:

- `-from-scratch`: remove every row first, then rebuild them all
- `-tasks <directory>`: the directory the server keeps tasks in (default $GUSTO_JOBS, else jobs)
- `-h, --help`: show this help

Environment:

- `GUSTO_DATABASE_URL`: where the index is kept: empty for usage.db beside the tasks directory, or a postgres:// address (a search_path parameter names the schema)
- `GUSTO_JOBS`: the directory of tasks, when -tasks is not given (default jobs)

Exit codes:

- `0`: the index holds every call in the records
- `1`: the index could not be read or written, or the run was interrupted
- `2`: usage error

Examples:

```sh
gusto usage reindex
gusto usage reindex -from-scratch
```

See also: `gusto usage sessions`, `gusto data`
